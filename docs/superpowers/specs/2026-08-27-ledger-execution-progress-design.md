# 项目台账执行进度整合设计（执行流水页下线）

日期: 2026-08-27
状态: 已批准
上游讨论: 执行流水独立页功能薄弱，整合进项目台账；时间线回放；结算语义澄清（用户 2026-08-27）

## 1. 背景与目标

现状：

- 执行流水独立页（`FlowsView` + `ExecutionFlowPanel`）：合同下拉 → 六向汇总卡 + 逐笔明细，
  无项目上下文，需要手动选合同，功能薄弱。
- 项目台账（`ProjectLedgerView`）：项目 → 合同卡（凭证齐套率五维 + 展开凭证明细），无执行进度。
- 后端已有 `computeExecutionProgress`（2026-08-27 物化层 spec §7）：数量口径执行进度，
  基准 = 台账合同数量 + 单位，量纲不一致如实降级；目前仅暴露给 agent 工具
  `query_execution_flows`，无 HTTP 出口。

目标：

1. 下线执行流水独立页，六向汇总与逐笔明细整合进项目台账合同卡。
2. 合同卡新增执行进度块：货物 / 资金 / 发票三组，已执行 vs 待执行，金额 + 数量双口径
   （资金/发票按金额，货物按数量；凭证带数量时一并展示）。
3. 时间线回放：拖动时间轴回放任一时点的三流累计状态。
4. 执行浮动如实呈现：进度不封顶，超额如实显示，整体标注「参考值」。
5. 资金/发票金额固定标注「未结算累计」。

### 业务口径（用户确认 2026-08-27）

- 合同只是约定框架：实际分批执行，批量围绕约定值浮动（约定 1 万吨，分三次各发 3000+ 吨）；
  批间单价随行情波动，货物发出/收到时价值并未确定。
- 价值在结算时才确定（结算单为后续独立需求，见 §7）。
- 因此：待执行 = 基准 − 已执行 仅为参考值；负数显示「超额 X」，百分比可超 100%，
  不封顶、不隐藏偏差。

## 2. 非目标

- 结算单功能：计算引擎、人工确认、入台账、进度基准改造 —— 单独需求（§7 记录口径）。
- 结算单据的识别与绑定。
- 币种建模与汇率换算（amount 保持原样）。
- 项目页（ProjectsView）的六向流水小表改造（维持现状）。

## 3. 后端：rollup 扩展（方案 B）

`rollupProject`（`apps/server/src/pipeline/projectRollup.ts`）对每份 confirmed 合同：

- 保留现有 `summarizeExecutionFlows`（项目级聚合不变）。
- 新增：`listExecutionFlows(ctx, no, userId)` + `computeExecutionProgress(flows, ledgers.get(no)?.fields)`；
  ledger map 本来就已查询，直接复用，无新增主数据查询。

`RollupContract` 增加 `execution` 块：

```ts
execution: {
  summaries: ExecutionFlowSummary[];   // 六向汇总，形状同 GET /api/bindings/flows
  progress: ExecutionProgress | null;  // computeExecutionProgress 返回值（序列化透传）
  flowCount: number;                   // 逐笔行数（卡片有无执行记录提示）
}
```

逐笔明细不进 rollup（控制响应体积），合同卡展开时按需调现有
`GET /api/bindings/flows?contractNo=`（该端点保留，不新增端点）。

## 4. 前端：合同卡执行进度块

### 4.1 卡片常驻行（最新状态）

齐套率行下方新增一行紧凑执行摘要，按合同角色取自然方向：

- 采购合同：收货数量 / 已付款 / 已收票
- 销售合同：发货数量 / 已收款 / 已开票
- 其他合同：有什么方向的数据显示什么

形如：`执行 62% · 发货 6,200/10,000吨 · 收款 300万/1,000万 · 开票 120万`。
百分比取货物口径 progress（可超 100%），无基准时省略。不带时间轴。

### 4.2 展开区（三段）

```
[执行进度块]   三行（货物/资金/发票）：已执行 | 待执行 | 基准，数字跟随时间轴
[时间轴回放]   离散步进滑杆 = 排序去重后的凭证日期序列，默认停在「最新」
[逐笔明细表]   全量展示，不随时间轴过滤（溯源/预览不变）
```

- 执行进度块：
  - 货物行：基准 = `progress.basis`（数量 + 单位）；待执行 = 基准 − 已执行（可超额）。
  - 资金/发票行：基准 = 合同金额，标注「合同额(参考)」；待执行 = 合同金额 − 累计，
    负数显「超额 X」。金额旁固定徽章「未结算累计」。凭证带数量字段时在金额下方
    加显数量小字（金额为主、数量为辅；单位各自成池不混算，与物化层口径一致）。
  - 块标题标注「参考值」。
- 时间轴回放：
  - 拖到时点 T → 进度块三行变为「截至 T 的累计」，前端对已拉取的流水行按
    `voucherDate <= T` 重算，不发请求。
  - 无凭证日期的行只在「最新」态计入（与 rollup 口径一致），回放态不包含，悬浮说明。
- 逐笔明细表：`ExecutionFlowPanel` 的明细表（FlowRow）迁入，溯源预览走 `FilePreviewModal`；
  展开时 lazy 拉取并按 contractNo 缓存。
- 主体名单未配置（`selfPartiesConfigured === false`）→ 进度块显示引导按钮跳主体名单页
  （复用 App 的 `openParties`，改挂到台账视图）。

### 4.3 降级与边界

- 合同台账无「数量/单位」→ 货物行只显已执行，待执行 '—'，`progress.reason`
  原样透传为悬浮提示。
- 合同无金额 → 资金/发票行只显已执行。
- 存在反向流水（与角色自然方向相反）→ 行尾「另有反向 N 笔」提示；
  项目级类型-方向校验仍归 rollup checks，不在卡片重复。
- 该合同无任何流水 → 「暂无执行记录」。

## 7. 后续需求：结算单（口径记录，单独立项）

用户口径（2026-08-27），作为下一份 spec 的输入：

1. 批次交货后，买卖双方对货物数量与质量进行确认。
2. 按合同原文中的质量调整/计价规则 + 本批次实际数量、化验数值，计算该批次实际价值。
   LLM 同时可见合同原文与批次凭证数值时，计算过程与结果可以做到完全准确。
3. 结算原为线下 Excel 过程，改为系统内置计算 + 人工确认 + 结果录入台账。
   计算能力不做通用大而全功能：**按商品类型拆分计算技能包**（用户 2026-08-27 确认），
   动态按商品类型加载 —— 不同商品（能源/化工/金属等）的质量调整与计价规则差异性大，
   技能包各自演进互不影响，与 Agent 工具设计哲学中 Skill + 通用执行器的形态一致。
4. 结算单金额 = 最终应付/应收金额与开票金额（价值确认事件）。
5. 上线后进度口径改造：资金/发票流的「应执行」基准从合同金额改为 Σ已结算金额，
   未结算批次维持暂估；合同金额退为参考线。本次设计的「未结算累计」标注与
   「合同额(参考)」措辞为其预留，不阻塞。
